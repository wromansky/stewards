# jobs: The brief/submit job cycle\: renders and writes a role's brief with its header, validates the typed answer against it, writes the updates and retires the brief, and appends telemetry.

## Overview

The jobs unit is the hand-off between the tool and the agent that does a piece of work. The tool writes a brief for one role on one unit (or for the architect, who has no unit), the agent answers in typed JSON, and submitting that answer checks it against the brief, writes the resulting updates, and retires the brief. The brief carries the answer schema, with each field's length cap stated in it, and tells the agent that a field over its cap is rejected. Where the answer carries a card patch, submit also applies it to the unit's card: each list updates entries by key, and only the explicit remove lists delete. Each submit leaves one line of telemetry, so you can see how large the packs were and how many anchors agents had to open. It lives in src/brief.rs, src/submit.rs and src/telemetry.rs.

## How it works

Building a brief packs and frames a role's context (build in src/brief.rs). It refuses an unsafe repo root (unsafe_path), and a validator brief with no unjudged bug is a usage error. The framing ends with the answer schema, the answer path, the submit command and the cap warning. The brief goes to .stewards/briefs/&lt;unit>-&lt;role>.md (architect.md; &lt;unit>-developer-&lt;n>.md, n from 1) through rel_path. Its first line is a stewards-job comment holding a JSON header that read_header parses; a missing file or bad header is no_brief. Submit (submit_file in src/submit.rs) needs a known unit, a header matching unit, role, task number and full tree id, and a regular answer file of at most 256 KiB, then runs the role's handler. A text field over its cap is reported as answer_too_long. For a card patch, check_patch validates before any write. Three upsert lists (interface by id, anchors by path and name, gaps by title) apply through put, which replaces the entry with the same key or appends; three remove lists apply last, and a removal must name a key the card has and not be upserted in the same patch. Writes go through write_remove_and_retire, which refuses link paths and returns card_changed before any write if a checked file changed; it writes in order, then removes the brief. Finally src/telemetry.rs appends one JSON line of sizes and counts to .stewards/telemetry/&lt;yyyy-mm>.jsonl; a failure only warns.

## How to change it

Start in src/brief.rs for what a brief says or where it lives, and in src/submit.rs for what an answer must satisfy or what a submit writes. Keep the header line format and the brief path scheme in step, because submit finds the brief by path and trusts the header to match. Build a job path only through rel_path. Print brief text only through emit, not println, so a closed pipe stays quiet. Keep the caps the schema states in step with the caps check_text enforces, so a brief never promises a limit submit does not check or the reverse. Keep write_remove_and_retire checking for changed files and link paths before it writes, and the brief removal last, so a failed submit leaves the brief to retry. For card patches, keep an omitted entry meaning keep: an entry leaves the card only by being named in a remove list that check_patch has checked. If you add a patch list, give it a key, a check in check_patch, and a line in the card change report. Keep telemetry to sizes and counts, never content, and never let it fail a submit. The tests are tests/brief.rs, tests/submit.rs, tests/submit_roles.rs and tests/developer.rs. Add the case to the matching file; for a change to what a brief contains, assert on the rendered brief text in tests/brief.rs.
