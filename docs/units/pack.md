# pack: Builds a role's context pack within the byte budget\: unit summaries, anchors with source windows, owned files, and diff hunks; the pack command.

## Overview

The pack unit builds the context a role is handed before it starts work: unit summaries, anchors with windows of source, the unit's owned files, and diff hunks. Everything has to fit a byte budget, set per role in repo.toml, so the reader gets the most useful slice of the repo that fits. It is exposed as the pack command, which prints JSON or, with --human, markdown. The architect gets no single unit but every unit's summary plus flows and decisions. The reviewer gets no single unit either: a round of review packs, each holding a section for every unit in its group, together all the units due for review. Every other role needs a unit. The developer role is the exception: it is built from a task of the maintainer's plan, not through the plain pack command.

## How it works

run takes an optional unit, a role, --diff and a task text (default git::task_text) and emits the pack for the current repo at its snapshot. pack assembles one role's pack. After a live stamp, --diff yields the changed files and their hunks; with no stamp it is a first review listing all owned files. [pack] exclude files are named, never inlined. developer builds the developer pack for task n: purpose, paths, interface, gaps, the unit's flows, the task, and only the card anchors in the task's files. The tester and reviewer packs list the unit's bug gaps as known_bugs (the reviewer's gaps exclude them), so a repeat defect is reported under its title. The reviewer's pack also lists the unit's answered findings (review --answer) for it to accept or contest once. For --role reviewer, run takes no unit and calls review with the units next says are due; the output is a round of groups, one review brief each. Each section is the maintainer's pack plus scenarios, test command and doc, with due_because naming why; hunks start at the oldest of the stamp and the tester and documenter marks. Units join a group in order while its rendering fits REVIEW_BUDGET (48000 bytes); the first that does not starts the next group, so every due unit is in exactly one group and none is deferred. A unit alone over budget is squeezed: fit, then doc, scenarios, then fenced bodies cut shorter. Each group lists the files changed in units not due. Budget is measured on the rendered markdown, which one_lines, table-escapes or fences free text and lists at most 200 owned files plus a count while JSON keeps all. fit drops, in order: halved source windows, sources last-first, gaps, known bugs, flows, a first review's owned files, hunks cut to 40 lines, each logged in dropped. Purpose, interface, task, scenarios, bug, answered findings and hunk paths are never dropped; a pack that still does not fit is over_budget.

## How to change it

Start in src/pack.rs: pack for what a role receives, developer for the developer pack, review, ReviewRound and ReviewPack for the reviewer's grouped packs, render for the markdown form, fit (and squeeze for a review section) for the shrink order, and run for the command's arguments. Tests live in tests/pack.rs; the review pack's are in tests/review.rs. Keep the budget honest: fit must measure the same render the --human output uses, so any new section needs both a render path and a place in the drop order, unless it belongs with the never-dropped content. Keep free text escaped or fenced in render so repository text cannot open a block or act as instructions. Keep excluded files named and not inlined, keep the 200-file listing cap in markdown with JSON carrying everything, and keep every drop recorded in dropped. If you change what the architect, the reviewer or a first review lists, update the matching test and the card's contracts.
