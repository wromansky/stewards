# next: Workspace state reports\: status (units, freshness, coverage, gaps, debt) and next (which review jobs are due, optionally writing their briefs).

## Overview

This unit answers two questions about a workspace: where do things stand, and what review work is due. `stewards status` prints one row per unit of every initialized repo: whether its review is fresh, stale or unreviewed, how many interfaces it has and how many a test scenario covers, its open gaps and bugs, and its debt. Repos never initialized are listed apart. `stewards next` is the gate before reporting done: it lists the review jobs (maintainer, tester, documenter, validator, sometimes an architect) due against the current snapshot, writes a brief for each, and exits 0 only when nothing is due and the checks pass. Each job names the files and reasons that triggered it. The tester and documenter fire on an interface's own lines changing, not on any edit to its file, so editing code elsewhere in the file does not call them. A unit never reviewed gets only its maintainer job (and a validator job for an unjudged bug); the tester and documenter wait for the first review's stamp.

## How it works

`status` (src/status.rs::status) walks each repo and compares each unit's stored review fingerprint with a fresh one: no stamp is unreviewed, a match fresh, a mismatch stale. It also counts interfaces, covered interfaces, gaps, bugs and debt. `status::run` always exits 0. `next` (src/next.rs::next) snapshots each repo and, per unit, builds jobs in fixed order. The maintainer job is due when the unit is stale or never reviewed, carrying the changed files (every owned file when there is no stamp) and debt lines added since the stamp. For the tester and documenter, interfaces_touched takes the card interfaces whose anchor file changed since the role's mark (falling back to the main stamp), parsed with Anchor::parse. It reads git::diff_hunks from the mark's tree to the snapshot and, per interface, finds its lines in the old and new file with anchors::interface_lines on git::blob_text. The interface counts as changed when a hunk, widened by one line each side, hits those lines; the reason is `interface changed: &lt;anchor>`. When the lines cannot be found (language not in BLOCK_LANGUAGES, no mark tree, no hunks, name absent, unreadable blob) the whole file counts: `interface file changed`. The tester also fires on a changed owned file under a test root; the documenter also when the card has interfaces but no docs. Both need a stamp. A bug with no severity gives a validator job. Two or more moved (stale, previously reviewed) units put an architect job first. `next::run` rejects --pr and exits 1 while any job or check failure remains.

## How to change it

Start with the per-unit block in src/next.rs::next for a due-job rule, and src/next.rs::interfaces_touched for what counts as an interface change. Keep a never-reviewed unit's maintainer job listing the unit's files, and keep it out of the architect's moved list, or the architect fires on every fresh init. Keep tester and documenter jobs gated on a stamp. Take interface files through Anchor::parse, not by re-splitting the anchor. Keep the fallback: when interface_lines cannot locate an interface, the file change must still count, so a job is never silently lost; it errs toward firing. interface_lines is a text heuristic (its simplified comment names the ceiling: a block can end early in a Python triple-quoted string or Rust raw string), so tighten it there rather than in next. Hunk sides come from git::diff_hunks; a deleted file, a C-quoted name or a binary has none, which also takes the fallback. Keep repo-prefixed paths in the architect's list, and keep status freshness and next staleness on the same fingerprint. Extend tests/next.rs and tests/status.rs with the rule you change and run them.
