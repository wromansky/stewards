# next: Workspace state reports\: status (units, freshness, coverage, gaps, debt) and next (which review jobs are due, optionally writing their briefs).

## Overview

This unit answers two questions about a workspace: where do things stand, and what review work is due. `stewards status` prints one row per unit of every initialized repo: whether its review is fresh, stale or unreviewed, how many interfaces it has and how many a test scenario covers, its open gaps and bugs, and its debt. Repos never initialized are listed apart. `stewards next` is the gate before reporting done. Plainly it lists, per repo, one reviewer job covering every stamped unit that is due, with each unit's reasons, plus a maintainer first-review job for each never-reviewed unit, and writes their briefs. `stewards next --roles` lists the deeper per-role jobs instead (maintainer, tester, documenter, validator, sometimes an architect), one brief each. Either way it exits 0 only when nothing is due and the checks pass. The tester and documenter fire on an interface's own lines changing, not on any edit to its file. A unit never reviewed gets only its maintainer job (and, with --roles, a validator job for an unjudged bug); the tester and documenter wait for the first review's stamp.

## How it works

`status` (src/status.rs::status) compares each unit's stored review fingerprint with a fresh one: no stamp is unreviewed, a match fresh, a mismatch stale; it also counts interfaces, covered interfaces, gaps, bugs and debt, and always exits 0. `role_jobs` in src/next.rs snapshots each repo and builds the per-role jobs per unit in fixed order: maintainer when stale or never reviewed (changed files, every owned file with no stamp, and debt added since the stamp); tester and documenter when interfaces_touched finds a card interface's lines hit by a git::diff_hunks hunk since the role's mark (widened one line each side; reason `interface changed: &lt;anchor>`), or the whole file counts (`interface file changed`) when anchors::interface_lines cannot place it; tester also on a changed owned test file, documenter also when needs_docs; both need a stamp. An unjudged bug gives a validator job; 2+ moved stamped units put an architect job first. `next` with roles writes each job's brief. Without, due_for_review folds each repo's stamped maintainer/tester/documenter jobs into one entry per unit, reviewer_job builds the review brief with brief::build_review and names units over the budget as next round, and never-reviewed maintainer jobs follow; architect and validator jobs are dropped. review_due gives brief and pack the same due list for one repo. `run` rejects --pr and exits 1 while any job or check failure remains.

## How to change it

Change a due-job rule in the per-unit block of role_jobs in src/next.rs, and what counts as an interface change in interfaces_touched; plain next and review_due both derive from role_jobs, so they follow. Change which jobs the reviewer folds in due_for_review, keeping a never-reviewed maintainer job out of it (it keeps its own first-review job). Keep a never-reviewed unit's maintainer job listing all its files and out of the architect's moved list. Keep tester and documenter jobs gated on a stamp. Take interface files through Anchor::parse. Keep the fallback: when interface_lines cannot locate an interface the file change still counts, so a job is never silently lost; tighten interface_lines itself, not next. Keep repo-prefixed paths in the architect's list, and keep status freshness and next staleness on the same fingerprint. Extend tests/next.rs (per-role rules, run with --roles) or tests/review.rs (the reviewer fold) and tests/status.rs, and run them.
