# next: Workspace state reports\: status (units, freshness, coverage, gaps, debt) and next (which review jobs are due, optionally writing their briefs).

## Overview

This unit answers two questions about a workspace: where do things stand, and what review work is due. `stewards status` prints one row per unit of every initialized repo: whether its review is fresh, stale or unreviewed, how many interfaces it has and how many a test scenario covers, how many open gaps and bugs it has, and how much debt. Repos that were never initialized are listed apart. `stewards next` is the gate before reporting done: it lists the review jobs (maintainer, tester, documenter, validator, and sometimes an architect) that are due against the current snapshot, writes a brief for each, and exits 0 only when nothing is due and the checks pass. Each job names the files that triggered it, so a reader of the brief knows where to look; for a unit never reviewed that means every file the unit owns, and the architect's list shows the changed paths, prefixed with the repo name in a workspace.

## How it works

Both commands start from the loaded workspace. `status` (src/status.rs::status) walks each repo, builds a router, reads the snapshot's file list, and compares each unit's stored review fingerprint with a freshly computed one: no review stamp means unreviewed, a match means fresh, a mismatch means stale. It then counts interfaces, interfaces some scenario names, non-bug gaps, bugs and debt lines. `status::run` always exits 0 and, with --telemetry, adds the current repo's telemetry summary, or null when no repo is current. `next` (src/next.rs::next) takes a snapshot of each repo and, per unit, builds jobs in a fixed order. The maintainer job is due when the unit is stale or never reviewed; the files it carries come from stale_files, which diffs against the stamped tree, or lists every file the unit owns when there is no stamp or git has pruned that tree. Debt lines added since the stamp are attached to that job. The tester job is due when an interface file or an owned file under a test root changed since the tester's mark, which falls back to the main stamp. The documenter job is due when an interface file changed since the documenter's mark, or when the card has interfaces but an empty doc. The validator job is due for a bug gap with no severity. Only units that were reviewed before and are stale go into the list of moved units; units never reviewed do not. If two or more units moved, an architect job is inserted first, its brief written from the first moved unit's repo, and its changed list is the union of the moved units' paths. When briefs are on, each job's brief is written in review mode. `next::run` rejects --pr as not implemented, and returns exit 1 when any job or check failure remains.

## How to change it

To add or alter a due-job rule, edit the per-unit block in src/next.rs::next; each role's rule is its own short section there, and the job closure fills in the snapshot, task and the brief command (with a --repo flag in a workspace). Keep the first-review behaviour true: a never-reviewed unit still gets a maintainer job whose changed list is the unit's files, and it must not count toward the architect's moved list, or the architect would fire on every fresh init. Keep paths in the architect's list repo-prefixed in a workspace, since several repos share it. Freshness in status and staleness in next both rest on the same fingerprint from the check module, so change them together. Keep status exiting 0 and next exiting 1 only for jobs or check failures. The tests are tests/next.rs and tests/status.rs; extend them with the rule you change, and run them before reporting done.
