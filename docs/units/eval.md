# eval: The eval runner\: suites and their manifests, arm setup, the Pi driver and transcript parser, the ritual gate and overhead report, and the fixture, tasks and seeded-bug repros it runs on.

## Overview

The eval unit is the runner behind `stewards eval`. It measures whether coding agents do better with stewards than without: it drives a harness (Pi, Claude Code or Hermes Agent) over a suite of tasks in several arms, parses every session transcript into a run record, checks that the full arm followed the ritual, and reports cost and token overhead. The graders never branch on the harness. It also holds the material it runs on under evals/: the fixture, task prompts, suite manifests, arms.sh, and one reproduction per seeded bug.

## How it works

run (src/eval/mod.rs) accepts pi, claude-code and hermes, picks the arms, loads the suite (suite.rs) and checks task numbers. pi.rs writes an isolated Pi agent dir; claude.rs an isolated CLAUDE_CONFIG_DIR; hermes.rs a template home (config lifting the one-shot cap of two subagents, .env linked, installs/ built) from which each session gets a fresh HERMES_HOME, and kills its gateway daemon after every session. Only pi takes --max-cost. execute reads every task prompt first, prepares the full arm once, then runs each task per run in every arm in a fresh copy. Each Driver starts a session (run_session, killing its group on timeout or on the runner's one SIGINT/SIGTERM handler) and parses its transcript into a Run: tokens (null when unmeasurable, timed out or interrupted), cost, files opened (content read or searched; a listing never), stewards commands, subagent launches (a refused Hermes delegate is none), reviewer submits, models and thinking. After each session the runner runs `stewards next --no-brief` and kills leftovers by cwd or HERMES_HOME. Hermes kept files have .env secrets [redacted]. grade.rs grades each task on gate misses only; overhead ratios are report-only.

## How to change it

Start in src/eval/mod.rs for the command, the plan, shared session helpers, the interrupt handler and the per-session loop; pi.rs, claude.rs or hermes.rs for a harness and its transcripts; grade.rs for verdicts and the report; suite.rs for manifest fields. Tests live in tests/eval.rs (the interrupt test in tests/eval_interrupt.rs, its own binary), with recorded transcripts under tests/fixtures/transcripts/&lt;driver>/. Keep true: never write the user's harness config; bare and block-only arms never see stewards on PATH; overhead ratios stay report-only; graders never branch on the harness; one files-opened rule on every driver; no task prompt contains `think`; the first session always runs under --max-cost; no fixture holds key material. A new harness needs a Driver, a branch in run, and its entry in src/harness.rs.

| kind | title | note |
|---|---|---|
| gap | Ritual steps are best-effort from transcripts | A stewards command is seen only as the program of a separator-split segment\: timeout/env/time prefixes, \`if stewards\`, \`{ ...; }\`, \`bash -c\`, and backticks are misread or missed (stated in RITUAL\_NOTE). |

| gap | reviewed\_units ignores --human output | simplified\: only JSON submit output is read; upgrade if reviewers start passing --human. |
